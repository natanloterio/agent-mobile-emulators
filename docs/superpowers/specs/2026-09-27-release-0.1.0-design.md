# Lançamento 0.1.0 — design

Data: 2026-09-27 · Branch: `feat/release-0.1.0`

## Objetivo

Publicar o Enxame 0.1.0 como projeto open source, com instaladores para Linux, macOS e Windows que funcionam sem
Node.js, sem a pasta do projeto e sem ler o README. O onboarding verifica e instala sozinho as dependências nos três
sistemas.

## Decisões da pessoa (não reabrir)

| Tema | Decisão |
|---|---|
| Entrega | Instaladores Linux, macOS e Windows |
| Público | Open source |
| Licença | AGPL-3.0-only |
| Dependências fora do Linux | O onboarding instala sozinho nos três sistemas |
| Assinatura | Sem assinatura na 0.1.0 (Gatekeeper/SmartScreen avisam; README ensina a abrir) |
| Onde gerar | Linux nesta máquina; macOS e Windows no GitHub Actions |
| Repositório | O atual (`natanloterio/agent-mobile-emulators`) vira público com todo o histórico, visual incluído |
| Runtime do daemon | Abordagem A: Electron 44 e o daemon rodando no próprio binário do Electron |

## 1. Runtime e empacotamento

- **Electron 33 → 44.4.5** (Node 24.21, Chromium 152). Node 24 é a mesma versão que o daemon exige hoje.
- **Daemon no binário do Electron.** `electron/daemon-bridge.ts` troca `spawn('node', ['--env-file-if-exists=.env',
  'dist-daemon/index.js'], { cwd: projectRoot })` por `spawn(process.execPath, [daemonEntry], { env: { ...process.env,
  ELECTRON_RUN_AS_NODE: '1' }, windowsHide: true })`.
  - `daemonEntry` em desenvolvimento: `<projeto>/dist-daemon/index.js`; empacotado: dentro de `process.resourcesPath`.
  - O `.env` só é lido em desenvolvimento (`app.isPackaged === false`): o main carrega o arquivo no `env` do filho.
  - Mantém o ouvinte `child.on('error')`.
- **Node.js sai do onboarding** (item `node`, fix `node-missing`, textos i18n e testes correspondentes).
- **electron-builder**, configurado no `package.json` (`build`):
  - Linux x64: AppImage e `.deb`.
  - macOS: `.dmg` x64 e `.dmg` arm64, sem assinatura de desenvolvedor; `identity: null` com assinatura ad-hoc para o arm64.
  - Windows x64: NSIS por usuário (`perMachine: false`, sem admin).
  - Fora do asar (`asarUnpack`/`extraResources`): `dist-daemon/**`, o binário nativo do `@napi-rs/keyring` da
    plataforma alvo, `daemon/vendor/scrcpy-server-v4.1` e `daemon/vendor/LICENSE-scrcpy`. O daemon precisa achar o
    scrcpy-server empacotado (`resolveVendor` em `daemon/src/config.ts` passa a considerar `resources/`).
- `package.json`: sai `private`, entram `license: "AGPL-3.0-only"`, `author`, `repository`, `homepage` e scripts
  `dist:linux`, `dist:mac`, `dist:win`.
- **CI** (`.github/workflows/release.yml`): disparado por tag `v*`. Jobs `macos-13` (x64), `macos-14` (arm64) e
  `windows-latest`: `npm ci`, testes, build, empacotamento, smoke test e upload para uma release **em rascunho**
  `v0.1.0`. O instalador Linux é gerado nesta máquina e anexado à mesma release.

### Imagem do sistema

`system-images;android-34;google_apis_playstore;arm64-v8a` em `darwin-arm64`; `…;x86_64` nos demais. O item do
onboarding mostra a arquitetura certa.

### Aceleração do emulador

- Com o emulador instalado: `emulator -accel-check` nos três sistemas (código de saída 0 = ok).
- Linux sem emulador ainda: checagem de `/dev/kvm` como hoje (`kvm-group`, `kvm-bios`).
- macOS: Hypervisor.framework, ok nas máquinas suportadas.
- Windows sem WHPX: item "Precisa de você" com fix novo `whpx-off`, comando
  `Enable-WindowsOptionalFeature -Online -FeatureName HypervisorPlatform` em PowerShell como administrador, e aviso de
  reiniciar.

### Hardware

- `darwin-arm64`: GPU = "Apple Silicon · memória unificada", `totalGiB` = 2/3 da RAM (Metal).
- `darwin-x64` sem NVIDIA: `gpu: null` (padrão "Só nuvem").
- Windows e Linux: `nvidia-smi`.
- Disco livre por `statfs` nos três.

### Chaveiro

Mesma sonda do `@napi-rs/keyring` (Keychain no macOS, Gerenciador de Credenciais no Windows).

### Caminhos

- Dados: `~/.local/share/enxame` nos três (o que o master já usa; sem migração).
- SDK: padrão por sistema que o master já resolve (`~/Android/Sdk`, `~/Library/Android/sdk`,
  `%LOCALAPPDATA%\Android\Sdk`), com `setup.json` como primeira opção.
- Ferramentas: `<dados>/tools`.

## 3. Limpeza para publicar

- `LICENSE` (texto integral AGPL-3.0) e `NOTICE` (scrcpy-server Apache-2.0 com `LICENSE-scrcpy`; Electron e Chromium
  levam as próprias licenças no pacote).
- Daemon: sai a semente automática da `conta1` (`@p1t41a.meta.test`, AVD `mcp_test_playstore`). Instalação nova
  começa sem identidades; bancos existentes não perdem nada. A base de clonagem continua `ENXAME_AVD_BASE` →
  `enxame_golden` → `mcp_test_playstore`; sem nenhuma, o erro explica como criar a `enxame_golden`.
- `src/state/fixtures.ts`: handles genéricos (`@conta.demo`…) no lugar de `@p1t41a`.
- `gitleaks` em todo o histórico antes de abrir o repositório. Achado real para tudo e vai para a pessoa.
- README: seção "Instalar" (links da release; abrir sem assinatura no macOS com botão direito → Abrir ou
  `xattr -dr com.apple.quarantine /Applications/Enxame.app`, e no Windows com "Mais informações" → "Executar assim
  mesmo"; o que o onboarding faz em cada sistema), aviso de Termos de Serviço mantido, "rodar do código" para quem
  desenvolve, selo da licença.
- `CHANGELOG.md` com a 0.1.0.

## 4. Publicação

1. Tudo entra no master por PR.
2. **Confirmação explícita da pessoa**, e então `gh repo edit --visibility public`.
3. Tag `v0.1.0` no master e push; o workflow gera macOS e Windows, roda os smoke tests e cria a release em rascunho.
4. Anexar AppImage e `.deb` gerados aqui.
5. **Confirmação explícita da pessoa**, e então publicar a release, marcada como pré-lançamento.

## 5. Verificação

- Com Electron 44: `npm test`, `tsc -b --noEmit`, `daemon:build`, `build`; Playwright E2E no Linux com o daemon
  subindo pelo binário do Electron; vídeo e miniatura ao vivo conferidos num emulador existente, só leitura.
- AppImage rodado sem a pasta do projeto, com dados, SDK e AVDs temporários; `.deb` conferido com `dpkg -x`.
- CI em `macos-13`, `macos-14`, `windows-latest`: instalador gerado e aberto; Playwright confirma onboarding na tela,
  itens da plataforma (imagem arm64 no Apple Silicon, `.exe` e WHPX no Windows) e daemon respondendo. Sem instalação
  real de vários GB.
- Testes unitários do onboarding rodam a mesma bateria por plataforma, com `platform`/`arch` injetados.

## Riscos declarados (CHANGELOG e README)

1. Instalação automática completa no macOS e no Windows validada só por testes unitários e smoke test do CI, nunca de
   ponta a ponta numa máquina real. A release sai como pré-lançamento e pede issues.
2. Sem assinatura: avisos do Gatekeeper e do SmartScreen.
3. Windows: WHPX exige administrador e reinício; o app só mostra o comando.
4. Traduções es/fr/de/zh sem revisão nativa.
