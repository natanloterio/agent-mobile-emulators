# Lançamento 0.1.0 — plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Gerar instaladores do Enxame 0.1.0 para Linux, macOS e Windows que rodam sem Node.js e sem a pasta do projeto, com o onboarding instalando as dependências nos três sistemas, e deixar o repositório pronto para virar público sob AGPL-3.0.

**Architecture:** O Electron sobe para 44 (Node 24.21) e o daemon passa a rodar no próprio binário do Electron (`ELECTRON_RUN_AS_NODE`). O onboarding ganha um módulo de plataforma (`electron/setup/platform.ts`) e uma tabela de downloads por plataforma (`artifacts.ts`); `paths.ts`, `probe.ts`, `hardware.ts` e `runners.ts` passam a receber a plataforma. O electron-builder empacota; o Linux é gerado aqui e macOS/Windows num workflow do GitHub Actions com smoke test por Playwright.

**Tech Stack:** Electron 44.4.5, electron-builder 26, Playwright 1.63 (`_electron`), TypeScript, zod 4, vitest, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-09-27-release-0.1.0-design.md`

## Global Constraints

- Plataformas suportadas pelo onboarding: `linux-x64`, `darwin-x64`, `darwin-arm64`, `win32-x64`; qualquer outra → `supported: false` e o app abre como hoje.
- Electron exatamente `44.4.5`; electron-builder `^26.15.3`; Playwright `1.63.0` (devDependency, sem baixar navegadores: `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`).
- Licença `AGPL-3.0-only`. Autor `Natan Loterio <natan@gaiahub.ai>`. Repositório `https://github.com/natanloterio/agent-mobile-emulators`.
- Downloads fixados exatamente como a tabela da spec §2 (URLs, checksums, tamanhos). Nada de "latest".
- Dados em `~/.local/share/enxame` nos três sistemas (ou `ENXAME_DATA_DIR`); SDK padrão por sistema: `~/Android/Sdk`, `~/Library/Android/sdk`, `%LOCALAPPDATA%\Android\Sdk`; ferramentas em `<dados>/tools`.
- Imagem do sistema: `system-images;android-34;google_apis_playstore;arm64-v8a` em `darwin-arm64`, `…;x86_64` nas demais.
- Nada pede sudo/admin automaticamente; o que exige admin vira item "Precisa de você" com o comando.
- Todo texto de tela passa pelo i18n nos seis idiomas (pt, en, es, fr, de, zh); o teste `src/i18n/i18n.test.ts` exige chaves e placeholders iguais.
- Estilo do repo: comentários curtos em português, `readonly`/imutabilidade, zod em toda fronteira.
- Commits `feat(release): …`, `fix(release): …`, `chore(release): …`, `docs(release): …`, sem linha de atribuição.
- Tornar o repositório público e publicar a release só com confirmação explícita da pessoa (Task 11).

## Review Focus

1. **Daemon empacotado não sobe** (asar: `node:sqlite`, `@napi-rs/keyring` e `ws` carregados de dentro do `app.asar` com `ELECTRON_RUN_AS_NODE`): o smoke test (Task 8/9) precisa provar que `daemon.json` aparece e `GET /state` responde a partir do app empacotado, não do projeto.
2. **scrcpy-server dentro do asar**: o `adb push` é um processo externo e não lê `app.asar`; o caminho entregue ao daemon precisa ser o de `app.asar.unpacked`. Teste unitário em `daemon/test/config-vendor.test.ts` (Task 2).
3. **Windows**: `sdkmanager.bat` não roda por `spawn` direto (Node ≥ 20.12 recusa `.bat` sem shell), então vai por `cmd /c`; binários com `.exe`; separador de PATH `;`. Testes em `electron/setup/runners.test.ts` (Task 5).
4. **Quem já usa o Enxame no Linux** não pode perder nada: banco com a `conta1` continua funcionando depois que a semente sai (Task 7), o `setup.json` antigo continua válido e o onboarding não reaparece. Teste em `electron/setup/startup.test.ts` (Task 4) e conferência manual na Task 8.
5. **Pacote do Ollama com layout diferente do esperado** (binário fora de `bin/`): o instalador precisa falhar com mensagem clara em vez de gravar um `ollamaBin` que não existe. Teste em `runners.test.ts` (Task 5).

## Ajuste em relação à spec

A spec §2 previa `emulator -accel-check`. Na hora da verificação o emulador muitas vezes ainda não está instalado, então a aceleração passa a ser checada pelo próprio sistema: `/dev/kvm` (Linux, como hoje), `sysctl -n kern.hv_support` (macOS) e `Win32_OptionalFeature` `HypervisorPlatform` pelo PowerShell sem admin (Windows). O fix `whpx-off` fica como na spec; entra também `hvf-off` para o macOS raro sem Hypervisor.framework.

- [ ] **Step 3: Implementar em `electron/daemon-bridge.ts`**

Acrescentar `import { parseEnv } from 'node:util';` e substituir `ensureDaemon` por:

```ts
export interface DaemonSpawn { readonly cmd: string; readonly args: string[]; readonly cwd: string; readonly env: NodeJS.ProcessEnv }

/**
 * O daemon roda no próprio binário do Electron (ELECTRON_RUN_AS_NODE; Electron 44 = Node 24, com node:sqlite).
 * Empacotado, o código está em `<resources>/app.asar/dist-daemon`; em desenvolvimento, no projeto, com o `.env` do
 * projeto somado ao ambiente (o ambiente vence).
 */
export function daemonSpawnSpec(o: {
  readonly isPackaged: boolean; readonly appPath: string; readonly resourcesPath: string; readonly execPath: string;
  readonly env: NodeJS.ProcessEnv; readonly dotenv: string | null;
}): DaemonSpawn {
  const fromFile = !o.isPackaged && o.dotenv ? parseEnv(o.dotenv) : {};
  return {
    cmd: o.execPath,
    args: [path.join(o.appPath, 'dist-daemon', 'index.js')],
    cwd: o.isPackaged ? o.resourcesPath : o.appPath,
    env: { ...fromFile, ...o.env, ELECTRON_RUN_AS_NODE: '1' },
  };
}

/** Sobe o daemon se não houver um vivo. `windowsHide`: no Windows, sem ele o daemon abre uma janela de console. */
export function ensureDaemon(spec: DaemonSpawn): ChildProcess | null {
  const info = readInfo();
  if (info && alive(info.pid)) return null;
  const child = spawn(spec.cmd, spec.args, { cwd: spec.cwd, stdio: 'inherit', env: spec.env, windowsHide: true });
  // Sem este ouvinte um erro de spawn derrubaria o main; o waitForInfo expira e a tela mostra o erro.
  child.on('error', (e) => console.error('[enxame] não deu para subir o daemon:', e.message));
  return child;
}
```

Atenção à ordem no teste de desenvolvimento: `{ ...fromFile, ...o.env }` faz o ambiente vencer o `.env` (`ENXAME_PORT: '1'`), mas a ordem das chaves do objeto esperado no teste é só visual — `toEqual` não compara ordem.

import path from 'node:path';
import { imageAbi, isWindows, platformId, type PlatformId } from './platform.js';

/** Onde o onboarding lê e instala. Tudo no home da pessoa: nada pede sudo/admin. */
export interface SetupPaths {
  readonly platform: PlatformId;
  readonly dataDir: string; readonly setupFile: string;
  readonly sdkRoot: string; readonly sdkmanager: string; readonly adbBin: string; readonly emulatorBin: string; readonly imageDir: string;
  readonly toolsDir: string; readonly jreDir: string; readonly javaHome: string; readonly javaBin: string; readonly downloadsDir: string;
  readonly ollamaDir: string; readonly ollamaBin: string; readonly ollamaModels: string;

/** SDK padrão de cada sistema; mesmas regras do daemon (daemon/src/device/sdk.ts). */
function defaultSdk(env: NodeJS.ProcessEnv, home: string, pl: PlatformId, p: path.PlatformPath): string {
  if (pl.startsWith('darwin')) return p.join(home, 'Library', 'Android', 'sdk');
  if (isWindows(pl)) return p.join(env.LOCALAPPDATA || p.join(home, 'AppData', 'Local'), 'Android', 'Sdk');
  return p.join(home, 'Android', 'Sdk');
}

export function resolveSetupPaths(
  env: NodeJS.ProcessEnv = process.env, home: string = os.homedir(), savedSdkRoot: string | null = null,
  platform: PlatformId = platformId() ?? 'linux-x64',
): SetupPaths {
  const win = isWindows(platform);
  const p = win ? path.win32 : path.posix;
  const exe = win ? '.exe' : '';
  const dataDir = env.ENXAME_DATA_DIR || p.join(home, '.local', 'share', 'enxame');
  const toolsDir = p.join(dataDir, 'tools');

  const ollamaBin = platform === 'linux-x64' ? p.join(ollamaDir, 'bin', 'ollama') : p.join(ollamaDir, `ollama${exe}`);
  return {
    platform, dataDir, setupFile: p.join(dataDir, 'setup.json'),

export const WHPX_QUERY = "(Get-CimInstance Win32_OptionalFeature -Filter \"Name='HypervisorPlatform'\").InstallState";

/** Aceleração do emulador pelo próprio sistema (o emulador pode ainda não estar instalado). */
async function probeAccel(platform: PlatformId, d: ProbeDeps): Promise<DepStatus> {
  if (platform.startsWith('darwin')) {
    return (await d.exec('sysctl', ['-n', 'kern.hv_support']))?.trim() === '1' ? ok('kvm', 'Hypervisor.framework') : user('kvm', 'hvf-off');
  }
  if (platform === 'win32-x64') {

  }
  if (!(await d.exists('/dev/kvm'))) return user('kvm', 'kvm-bios');
  return (await d.canReadWrite('/dev/kvm')) ? ok('kvm', '/dev/kvm') : user('kvm', 'kvm-group');
}
